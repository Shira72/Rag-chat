# מטלת בית / ביצוע – צ'אט הוראות תכ"ם

## חלק א' – זיהוי בעיה ותכנון פתרון

לאחר חקירה של אתר הוראות תכ"ם זיהיתי בעיה שניתן לפתור באמצעות תוכנה:

**הבעיה** – האתר מכיל הרבה מאוד מידע, פרטים, פרקים ותתי-סעיפים בנושאים שונים. משתמש יכול לחפש מידע הרבה זמן. הוא יכול להגיע לנושאים דומים אך שונים ממה שהוא מחפש, וזה עלול לגרום לבלבול ולחוסר יעילות. כמו כן יש מהדורות שונות, וייתכן שהדבר שהוא מחפש קיים במהדורה ישנה, וכך החיפוש הופך למתיש ומייגע. בנוסף, גם לאחר שמצא את דף ההוראות הנכון, עליו לקרוא בדקדוק רב את כל הסעיפים ותתי-הסעיפים עד לקבלת התמונה השלמה. לסיכום, המערכת מורכבת לחיפוש בתוכן עצמו ולסיכום המידע.

**הפתרון** – הצעתי לפתור את הבעיה באמצעות צ'אט ייעודי להוראות תכ"ם. המשתמש שואל שאלה, והמערכת מחפשת תשובה במקורות המידע שלה (הוראות, טפסים וכו'). אם נמצאה תשובה מתאימה, הצ'אט מחזיר תשובה עם קישור למקור. אם לא נמצאה תשובה, הצ'אט לא ימציא מעצמו אלא יחזיר "לא מצאתי", ובכך ישמור על דיוק ואיכות התשובות. בצורה זו פתרתי את החיפוש המייגע בצורה מועילה, נוחה ונעימה למשתמש.

**התכנון הטכני** – הרכיב המרכזי הוא מערכת RAG עם שני חלקים (RAG – כלומר התשובות נלקחות אך ורק מדפי הוראות התכ"ם שנקלטו במערכת, ולא מחיפוש במקורות אחרים או מהמצאה). שני החלקים הם:

- **קליטה** – קבצי ה-Word נקראים, מספרי הסעיפים מחושבים, הטקסט מחולק לקטעים, וכל קטע הופך לווקטור ונשמר באינדקס. זה קורה פעם אחת לכל קובץ, וכשמוסיפים או משנים קבצים מריצים פקודת עדכון שמעבדת רק את מה שהשתנה.
- **מענה** – על כל שאלה מתבצע חיפוש היברידי, גם לפי משמעות וגם לפי מילים ומספרי סעיפים. הקטעים הרלוונטיים עוברים למודל שפה, שעונה רק מתוכם. כל ציטוט נבדק בקוד מול המקורות, והתשובה חוזרת למשתמש עם קישור לסעיף המדויק. אם אין מקור מתאים, המערכת עונה "לא מצאתי".

המערכת משתמשת במודלים של OpenAI להפיכת טקסט לווקטור (בקליטת הנתונים ובכל שאלה), ולניסוח התשובה מתוך הקטעים שנמצאו.

הטכנולוגיה שבחרתי היא Python, מכמה סיבות: הקבצים של הוראות תכ"ם הם קבצי DOCX, וב-Python יש את python-docx, שהיא הספרייה הוותיקה והמלאה ביותר לקבצי DOCX. בנוסף, ב-Python הכלים לבניית RAG מגיעים בגרסה המלאה והעדכנית ביותר, בעוד שבשפות אחרות חלקם חסרים, ורוב הדוגמאות והידע בתחום כתובים ב-Python.

## חלק ב' – פיתוח POC

### דרישות מקדימות

- Python 3.12
- מפתח API של OpenAI. הרשאות מומלצות (Restricted): **Embeddings – Write** ו-**Chat completions – Write** בלבד.

### התקנה (פעם אחת)

מתוך תיקיית הפרויקט (`rag-chat`):

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

לאחר מכן מעתיקים את הקובץ `.env.example` לקובץ חדש בשם `.env`, ומכניסים בו את המפתח:

```
OPENAI_API_KEY=<המפתח שלך>
```

> הקובץ `.env` מכיל סוד ואין לשתף אותו.

### שלב 1 – קליטת המסמכים

מעתיקים את קבצי ה-Word (`.docx`) לתיקייה `data/docs`, ומריצים:

```powershell
.\.venv\Scripts\python.exe -m app.ingestion.ingest
```

הפקודה קוראת את הקבצים, מחשבת את מספרי הסעיפים, מזהה מהדורה נוכחית ומהדורות קודמות, ובונה את אינדקס החיפוש. בהרצות הבאות היא מעבדת רק קבצים חדשים או ששונו, וקובץ שנמחק מהתיקייה מוסר מהאינדקס. לבנייה מחדש מאפס מוסיפים `--rebuild`.

### שלב 2 – הפעלת הצ'אט

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.api:app --port 8000
```

כשמופיעה השורה `Uvicorn running on http://127.0.0.1:8000`, פותחים בדפדפן: **http://localhost:8000**

כדי לעצור את השרת: `Ctrl+C` בטרמינל.

### שאלה מהטרמינל (לבדיקה, בלי דפדפן)

```powershell
.\.venv\Scripts\python.exe -m app.ask --debug "תוך כמה ימים צריך לשלם לספק?"
```

עם `--debug` מוצגים גם הקטעים שהחיפוש מצא והציון של כל אחד.

### בדיקות

## חלק ג' – חשיבה הנדסית והתאמה ל-PROD

**1.** השיקול המרכזי בתכנון הפתרון הוא שמירה מוקפדת על המידע, כך שלא יחזור למשתמש מידע לא מדויק או שגוי. לכן המידע שחוזר הוא רק כזה שנמצא במקור, עם קישור למקור, וניתנת עדיפות לתשובה "לא מצאתי" על פני תשובה שגויה.

בחרתי לא לממש חיפוש גם בתוך הקישורים החיצוניים שיש בקבצים, כיוון שתוכן חיצוני יכול להשתנות, ואין עליו שליטה. עם זאת, הקישורים עצמם יחזרו אליו כשהם רלוונטיים לתשובה, ואם יתעניין יוכל להיכנס לקישור ולראות שם את הפרטים.

בנוסף, באתר עצמו מופיעים תאריכי המהדורות השונות. החלטתי שעדיף כרגע לשמור על שלמות המקור בלי להוסיף את התאריכים האלה, ולכן אם נבקש מידע על תאריך מסוים, לא בהכרח שהמערכת תדע לענות. זה בהחלט דבר שהייתי מוסיפה כדי לשפר את איכות התשובות.

השינוי המשמעותי שהייתי מבצעת הוא העברת כל הנתונים למסד נתונים אחד, עם טבלת מסמכים מפורשת. היום הנתונים מפוזרים בכמה מקומות: קבצי JSON, מאגר וקטורים מקומי ואינדקס בזיכרון. זו הייתה בחירה מכוונת, כדי שהדמו ירוץ בלי הקמת מסד נתונים.

מסד נתונים אחד ישפר את התחזוקה, כי יהיה מקור אמת אחד, והקשר בין המהדורות יישמר במפורש ולא יוסק לפי שם (כיום המערכת קובעת את המהדורה הנוכחית לפי מספר המהדורה הגבוה ביותר). הוא גם יאפשר גדילה: כל השרתים יעבדו מול אותם נתונים, במקום שכל שרת יטען הכול לזיכרון שלו ויצטרך טעינה מחדש אחרי כל קליטה של קבצים.

**2.** את ההעלאה הייתי הופכת לאוטומטית: כל עדכון נבדק ועולה קודם לסביבת בדיקות, ורק אם הכול תקין הוא עולה גם ל-production. בנוסף הייתי מוסיפה ממשק אדמין להעלאת קבצים וניהול מהדורות, כדי שמנהלי התוכן לא יצטרכו להריץ פקודות.

כדי לדעת שהמערכת באמת עובדת, הייתי מוסיפה בדיקות שרצות כל הזמן, וגם מיד אחרי כל העלאה. הבדיקות שולחות שאלות שהתשובות עליהן ידועות מראש, ובודקות שחוזר אותו סעיף ולא "לא מצאתי". הכול נשמר בלוגים, ואם משהו משתבש נשלח מייל לאחראי על המערכת.

תרחיש כשל: המערכת מחזירה "לא מצאתי" כל הזמן, למרות שהנתונים קיימים, ואין שום שגיאה. דבר ראשון הייתי בודקת אם המסמכים נטענו. אם לא, הלוג של הקליטה יראה איפה זה נכשל. אם המסמכים נטענו, הייתי בודקת מה החיפוש מצא לשאלת הבדיקה, וכך מבינה איפה הבעיה.
